# Spec：切片 12，模块产物改档（第二批）

> 2026-11-22，autopr-design。总账 `research/2026-11-18-自动PR系统设计/batch-2-auto-merge-spec.md`（第二批规格，用户已批准，原话"批准"）的切片 12，对应假设 B13。
> 起因：切片 4 回放发现，模块 PR 几乎都改了 `spec/**`、`tasks/**` 的内容，全部算 T4，开了接管也没有 PR 能自动合并。

## 规则

- `spec/**`、`tasks/**` 的内容改动默认是 **T4**，不变（只勾 todo、只改批准标记仍是 T1）。
- 下面四条同时满足时，降为 **T2**：
  1. 这个 PR 属于某个 spec-guard 模块：它有绑定当前 head 的最终验收记录（切片 10 增补）；
  2. 改的是**这个模块自己的**产物：`spec/<模块>.md`，或 `tasks/<模块>/` 下的文件；
  3. 本机编排在 **head 提交**上运行 spec-guard 0.91 的 `hooks/map_view.py --json`，结果显示这个模块的 Spec 和 Plan 都是 `approved` 或 `codex-approved`，而且 `reviewApprovedBy` 不为空。这表示批准仍然有效：文件批准后没改过，并且如果是 Codex 批的，接管档位确实允许这一步交给 Codex；
  4. 编排把核对通过的路径写进证据评论：`"artifacts": {"module", "verified": [...]}`。证据评论必须是机器人发的、没被编辑过、绑定当前 head。
- **永远不降**：
  - `spec/CAPABILITY-MAP.md`：新模块要人批；
  - 别的模块的产物；
  - `.agent/**`：共用规则里本来就是 T4，接管配置在这里，改它就是放宽档位；
  - 任何命中其他 T3/T4 保护规则的文件。
- 准入（Actions 和本机重算是同一份代码）从证据里读 `verified`，传给风险分级。没有合格证据，就什么都不降。

## 编排里的顺序

风险预检发生在跑检查之前，那时还没核对。所以 spec-guard 项目的预检先**假设**这些产物会核对通过，不让它们在预检就被挡下。最终是否降档，以证据为准：在合并前重算的准入里决定，核对不过就停在「admission」，理由里写着 T4。

## 验证

- 单元测试覆盖：已核对降为 T2、没核对仍是 T4、能力图和 `.agent` 永远 T4、别的模块的产物不降、Spec 已修订（`revised`）不降、Codex 的批准不被接管档位认可时不降、没有 map_view 时不降。
- 用 module-crew 的真实 `map_view.py --json` 输出试过核对函数，结果正确。
