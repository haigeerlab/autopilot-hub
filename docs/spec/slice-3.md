> 上游：设计 r6（总账 `research/2026-11-18-自动PR系统设计/README.md`）§3.4 降级、§6.1 成功标准 ③；切片 2 规格（降级 issue 格式）；repo-readiness v0.3.1 的复检与掉档信号（readiness-tool #21672、#21686）。

## 0. 先要你定的一件事：复检在哪里跑

我原先设想放在 GitHub Actions 上，读了 repo-readiness 的探针源码后发现一个问题：

- 最关键的三条"立即掉档"条款里，**G2（分支保护、规则集的绕过名单）、G5（秘密扫描）要读仓库的管理类信息**（`branches/<b>/protection`、`security_and_analysis`）。Actions 自带的 token 拿不到这类权限，这两条在 CI 上只能判"无法判定"，而"无法判定"既不计次、也不触发掉档。
- 也就是说，放在 CI 上跑，**最该停的情况恰好停不下来**，和"出事停得住"的目标相反。

| 选项 | 好处 | 代价 |
| --- | --- | --- |
| **A. 在你的 Mac 上每周跑（推荐）** | 用你本机已登录的 `gh`，G2、G5、G6 都能判；和"结论在本机签发"一致；不用新建任何凭据 | Mac 不在线那周就不跑（下次开机补跑）；降级 issue 以你的 GitHub 账号开出（agent 身份 Q2 建好后改用它） |
| B. 在 GitHub Actions 上每周跑 | 不依赖 Mac 在线 | G2、G5 判不了（见上），除非你新建一个带管理读权限的 token 放进仓库密钥，这又是一份长期凭据要管 |

**下文按 A 写。** 你选 B 的话，第 2、5、6 节要改。

## 1. 假设（请一并确认）

| # | 假设 | 不成立时 |
| --- | --- | --- |
| A1 | 复检在你的 Mac 上跑（见第 0 节），每周一次，用本机的定时任务（macOS `launchd`）触发；Mac 没开时，下次开机补跑 | 改用 GitHub Actions（第 0 节选项 B） |
| A2 | **复检用的 repo-readiness 必须是允许列表里的发布版**（现在是 0.3.1 的干净检出），不用开发中的代码。用哪一版由本机配置指定（掉档信号要 0.3.0 以上），不一定等于签发结论的那一版 | — |
| A3 | **尺子必须和接入结论里记的那把一致**：按结论 `basis.rulesets[].sha256` 核对。对不上（尺子换了）就**不判掉档**，只在报告里说明"尺子已变，需要重新签发结论" | 允许换尺子后照样判：会把"尺子变严"误当成"仓库变差" |
| A4 | **基线**：本机为每个仓库保存上一次复检的 `report.json`。第一次运行时，如果本机有签发结论所依据的那份报告（文件 sha256 等于结论的 `basis.report_sha256`），就用它作第一份基线；否则只建立基线、不判掉档 | — |
| A5 | 只读新报告的 `drop_signals`，不自己比较两份报告（readiness-tool 的约定）；降到的等级取信号里的 `to_trust_cap`，为 null 或不是 L0–L5 时按 L0 | — |
| A6 | 先自评、再裁决的条款（D1、R1 等）证据变了时，报告会留下待裁决请求。复检**不裁决、不签发新结论**，只用掉档信号；待裁决请求在运行摘要里列给你 | — |
| A7 | 降级 issue 沿用切片 2 的格式：标签 `autopilot:degrade`，`reason: "readiness-drop"`，`ref` 为新报告文件的 sha256，`evidence` 附信号条目；同一份报告只开一次 | — |
| A8 | 先只复检 agent-relay；其他仓库有了接入结论再加 | — |

## 2. 目标

仓库的就绪度掉档时（例如有人关掉了分支保护、关掉了秘密扫描），**一周之内**自动开出降级 issue，准入随即压低上限；不用等下一次人工重新签发结论。

## 3. 范围

| 做 | 不做 |
| --- | --- |
| 本机脚本 `recheck`：拉取被测仓库 main 的干净检出 → 用允许列表里的 repo-readiness 发布版跑 `check --baseline` → 读 `drop_signals` → 开降级 issue | 签发新结论（仍由人在本机签发、人合并） |
| 核对尺子与结论一致；不一致时不判掉档 | 裁决待裁决的条款 |
| 保存每个仓库的上一份报告作基线 | 回升（掉档后恢复）：仍由你关闭降级 issue |
| `launchd` 定时配置的示例，以及手动运行的命令 | 在 GitHub Actions 上跑（除非你选 B） |
| 运行摘要：掉档信号、待裁决请求、跳过原因 | 调 `module-crew tier degrade`（留给编排） |

## 4. 一次运行的步骤

1. 读配置（要复检哪些仓库、各自主 checkout 之外的工作目录）。
2. 对每个仓库：
   1. 从 GitHub 读默认分支上的接入结论；没有结论就跳过。
   2. 在工作目录里取默认分支最新提交的干净检出（只读，不在你的开发 checkout 里跑）。
   3. 按结论的 `basis.tool` 找到允许列表里对应版本的 repo-readiness 干净检出；不在允许列表里就跳过并说明。
   4. 按结论的 `basis.rulesets` 找尺子，sha256 不一致就只跑检测、不判掉档（A3）。
   5. 跑 `repo-readiness check ... --baseline <上一份报告>`。
   6. 有 `drop_signals`：按 A7 开降级 issue（已开过同一份报告的就跳过）。
   7. 把这次的报告存为下一次的基线。
3. 写运行摘要；任何一步出错，该仓库标"失败"并写原因，不开 issue，也不覆盖基线。

## 5. 安全

- 被测仓库只做干净检出、只读；`check` 默认不执行仓库代码（不带 `--exec-entries`）。
- 用你本机 `gh` 的登录，只调用读接口和"开 issue、写评论"两类写接口。
- 降级只会压低上限；解除仍要你亲手关 issue。

## 6. 放在哪里

| 东西 | 位置 |
| --- | --- |
| 脚本 `recheck/` + 单元测试 | autopilot-hub（T4） |
| `launchd` 配置示例、手动运行说明 | autopilot-hub 的 `examples/` |
| 本机配置、基线报告、运行日志 | 你 Mac 上的 `~/.autopilot/recheck/`（不进任何仓库） |
| 实际装上 `launchd` 定时任务 | 你本机，**要你同意后才装** |

## 7. 验收标准

1. 单元测试覆盖：
   - 有掉档信号就开 issue；
   - 没有信号、第一次没有基线、尺子不一致、工具不在允许列表、没有结论，这几种都不开；
   - 同一份报告不重复开；
   - `to_trust_cap` 为 null 或非法时按 L0；
   - 出错时不开 issue、不覆盖基线。
2. 本机对 agent-relay 手动跑一次：第一次建立基线；第二次（仓库没变）没有掉档信号、不开 issue。
3. 演练掉档：用一份人为构造的"上一份报告"（把某条立即掉档条款改成满足），跑一次，应开出 `readiness-drop` 降级 issue；你关闭后解除。
4. 装上 `launchd` 后（你同意后），一周后看到自动运行的记录。
