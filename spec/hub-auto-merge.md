## 目标

合并前验证通过后，不再靠本机守着去合并：hub 在验证过的提交上写提交状态 `autopilot/verified`，再把 PR 交给 GitHub 自动合并；本机巡检 `watch` 盯住 PR 和主干的 CI，CI 变红按三种情况分开处理，主干变红时停下、收紧档位、通知用户，任何一步出错或等太久也停下告诉用户。合并前验证里要 AI 操作的用例交给非作者的 AI 去做。这是自动驾驶第一版能力图第 2 行，对应总需求 R4、R6，成功标准 S3、S4、S5、S10、S11、S18、S19；依据的总体技术方案（已批）第 4.2～4.8、7、9 节和模块 1 批准稿（F3 v1.8、长期授权）。

## 给谁用

- 用户本人：确认需求以后不用再管合并，出事时收到通知、知道停在哪、为什么、可选的做法。
- 各插件仓库里按 spec-guard 新流程开发的会话（Claude Code 或 Codex）：开完 PR 调一次 `hub run`，之后的合并、盯 CI 不归会话管。
- 只覆盖六个插件仓库和沙盒（总需求假设 A1、A2）。

## 使用场景

- **U1 普通 PR 自动合并**：同时满足四条（F3 v1.8 自动路）：新流程模块；合并档位为 `auto`；本仓库主干的必需检查里有来源限定为 hub App 的 `autopilot/verified`；hub 判为非 T4。另外要求 hub 的 App 装在本仓库、权限够用，本机装好了 `watch` 定时任务。会话开 PR 后调 `hub run`；hub 验证通过 → 写 `autopilot/verified` → 记下 `validatedHeadOid` → 先打 `autopilot:authored` 标签 → 打开 GitHub 自动合并（`expectedHeadOid=validatedHeadOid`）。GitHub 等必需检查通过后合并；`watch` 发现已合并，打 `autopilot:auto-merged`、开跟进 issue、写事件。四条或部署前提任一不满足，不打开自动合并，走人工路。
- **U2 T4 PR 和其他人工路**：`hub run` 判为 T4、或档位不是 `auto`、或部署前提不满足时，照样跑完验证（现在风险不通过会提前停，`cli.py:754` 一带、`flow.py:534-535`，要改），通过就写 `autopilot/verified`，不打开自动合并，通知用户由用户在对话里说「合并」。
- **U3 合并前验证里的 AI 操作用例**：回归测试文档里执行方式为 `ai-operate` 的用例，hub 交给 delegate 的执行通道，由非作者的 AI 执行，交回「通过／不通过」和证据，写进验证报告；delegate 不可用时退回 `manual` 交用户（总体方案 4.3b；现在 `flow.py:475` 一律当人工用例）。会写文件的用例在一次性环境里执行，隔离方式在技术方案里定。
- **U4 PR 的 CI 变红**：`watch` 分类：环境问题自动重跑；CI 配置写错，AI 准备修改的 PR（T4）由用户合；测试失败，通知负责的会话分析，代码问题按修复上限修，判断为用例问题就停下交用户。
- **U5 主干 CI 变红**：分类后，测试失败就开降级 issue、立即收紧这个仓库的档位、关掉这个仓库已排队的自动合并、通知用户；不撤回、不发版。现有可复用 workflow `degrade.yml` 在主 CI 失败时直接开降级 issue，要改成按分类处理（各仓库 caller 升钉归 B 批）。
- **U6 验证后又推了新提交**：新提交没有 `autopilot/verified`，GitHub 不会合；`watch` 发现 head 变了，关掉自动合并，通知会话重新调 `hub run`。
- **U7 出错或等太久**：开 PR 失败、打开自动合并失败、CI 全绿却没合并、主干 CI 变红、`watch` 自身的一步失败，或自动合并打开 60 分钟还没合、单次 CI 超过 60 分钟：进入暂停并通知用户，说明出了什么事、试过什么、可选的做法和各自的代价。
- **U8 回滚**：用户说暂停自动驾驶时，冻结 → 关掉所有排队中的自动合并 → 必要时退回直接合并（`mergeMode: direct`）。

## 业务规则和异常情形

- **R4 风险分级**：只有这几类判 T4：`.github/workflows/`、发布配置和版本号文件、权限令牌密钥配置、hub 自己的接管配置。`spec/`、`tasks/` 等流程文件不再判 T4。T4 永远不打开自动合并，这是调用打开接口之前的硬性前置条件，判定写进证据评论。
- **只合验证过的内容**：打开自动合并时带 `expectedHeadOid=validatedHeadOid`；`autopilot/verified` 只写在验证过的那个提交上。squash 合并会生成新的合并提交，要求的是合进主干的内容等于验证过的那个提交，不是两者 SHA 相同。这个状态只表示「合并前验证通过」，不表示「可以自动合并」。
- **检查已全绿时**：打开自动合并被拒绝时，先读 PR 当前 head 和必需检查：head 仍是 `validatedHeadOid` 且必需检查全部成功，才按这个提交直接合并（带 sha）；head 对不上时短暂重试（沙盒实测推送后约 4 秒才对上），重试后仍对不上就当成 head 被改了；其他情况停下。不凭报错文字判断。
- **CI 三分类**（R6）：环境问题（失败在测试之前的 step，或重跑后变绿）自动重跑最多两次，不收紧；CI 配置写错，AI 准备修改（T4）由用户合；其余一律按测试失败，判不准往严里判。测试失败由会话分析是代码还是用例的问题，写明依据；用例问题停下交用户，AI 不能自行判为用例问题放行。
- **修复上限**：同一项检查、同一条回归用例、同一条审查意见算同一个原因；CI 失败、合并前验证失败、审查阻断三种来源共用两次上限，计数持久记在 `watch-state.json`。改了代码后重新跑一遍失败的那项算修一次。到上限就停下，说明出了什么事、试过什么、可选的做法和各自的代价。修复时改了已有的测试文件或回归测试文档（以需求开工基线为准，新增文件不算），立即暂停交用户。
- **暂停**：持久的终态；PR 暂停时关闭自动合并。PR 级的暂停在用户明说或重新验证通过后离开；**仓库级收紧**（主干变红）只在用户说恢复后离开，重新验证通过不算。
- **不丢、不重做**：每个副作用（打标签、开 issue、发评论、发通知）带幂等键，做完逐项记下；通知先入队，发成功才出队。
- **单实例**：`watch` 同一时间只跑一个。
- **自动连着做之前先说一句**：`hub run`、`watch` 的每一串动作，先写一条「将要做什么」进事件，并通知负责的会话。
- **回滚开关**：`~/.autopilot/config.json` 的 `mergeMode`（`automerge`｜`direct`，默认 `automerge`）；`watch --freeze` 之后只做关闭类动作。

## 不做什么

- 不做发版（模块 3 `hub-release`）；主干绿后只记下目标提交和关联 PR，交给模块 3。
- 不改 spec-guard 的关卡和档位规则（模块 4、5）。
- 不做汇报的汇总成文（模块 8）；本模块只把事件写进 `watch-state.json` 和证据评论。
- 不自动撤回已合并的改动，不替用户关降级 issue。
- 不在各仓库上动手：加必需检查、装 launchd、升钉都是 B 批，由 ecosystem-lead 组织、用户在 GitHub 上做；本模块交付 B 批要用的东西（见下一节）。
- 不迁移老流程模块，不改老流程的最终验收要求。

## 交给 B 批和模块 3 的东西

- B 批：`watch` 的 launchd plist 模板和安装、卸载命令；`degrade.yml` 新版本的提交号（供 caller 升钉）；逐仓库「加 `autopilot/verified` 必需检查前要满足什么」的检查清单。
- 模块 3：主干 CI 绿时的发版目标提交、关联的 PR 和它的合并前验证证据在哪里读（`watch-state.json` 的字段），因为主干上的新提交没有 `autopilot/verified`。

## 成功标准

- **S1** 沙盒里一个满足 U1 四条的 PR，调一次 `hub run` 后：先有 `autopilot:authored` 标签，再打开自动合并；由 GitHub 自动合并；合进主干的内容等于写了 `autopilot/verified` 的那个提交；这期间没有任何本机进程在等。（总需求 S3）
- **S2** 部署前提缺一条（例如主干必需检查里没有 `autopilot/verified`）：不打开自动合并，走人工路。
- **S3** T4 的 PR 跑完验证、拿到 `autopilot/verified`，但没有被打开自动合并，用户收到「由你合并」的通知。（S4）
- **S4** 合并前验证没通过的 PR 既没有 `autopilot/verified`，也没有被打开自动合并，也没有被合并。（S5）
- **S5** 打开自动合并后再推一个提交：GitHub 不合并新提交；下一轮 `watch` 关掉自动合并并通知会话。
- **S6** 检查已全绿时调 `hub run`：读到 head 等于验证过的提交且必需检查全部成功，才直接合并；head 不对时不合并。
- **S7** `ai-operate` 用例由 delegate 执行并写进验证报告；delegate 不可用时转为 `manual`。
- **S8** PR 上的 CI 失败按三种分：环境问题重跑、绿了继续、不收紧；配置问题产出一个 T4 修改 PR、由用户合；测试失败通知会话，判为用例问题时停下交用户。（S18）
- **S9** 同一个原因在三种来源之间累计到第三次修复之前停下，给出可选做法和代价；修复改了已有测试或回归测试文档时立即暂停。（S10）
- **S10** 主干 CI 因测试失败变红：开降级 issue、该仓库档位立即收紧、该仓库已排队的自动合并都被关掉、用户收到通知；没有撤回，没有触发发版；重新验证通过不会恢复，用户说恢复才恢复。（S19）
- **S11** U7 列的每一种出错和超时：进入暂停并通知用户，不空等、不跳过。（S11）
- **S12** 回滚第 1～3 步在沙盒逐步验证通过：冻结后 `watch` 没有新的打开事件；排队中的自动合并全部关掉；`mergeMode=direct` 时 `hub run --dry-run` 显示走直接合并。
- **S13** `watch` 停了一段时间（模拟休眠）后再跑：从 `watch-state.json` 接着处理，不重复开 issue、不重复发通知。
