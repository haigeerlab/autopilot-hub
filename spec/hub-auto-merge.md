# 需求：hub-auto-merge

<!-- spec-guard: flow v2 tier=important -->

## 目标

合并前验证通过后，不再靠本机守着去合并：hub 在验证过的提交上写提交状态 `autopilot/verified`，再把 PR 交给 GitHub 自动合并；本机巡检 `watch` 盯住 PR 和主干的 CI，CI 变红按三种情况分开处理，主干变红时停下、收紧档位、通知用户，任何一步等太久也停下告诉用户。这是自动驾驶第一版能力图第 2 行，对应总需求 R4、R6，成功标准 S3、S4、S5、S11、S18、S19；依据的总体技术方案（已批）第 4.2～4.8、7、9 节。

## 给谁用

- 用户本人：确认需求以后不用再管合并，出事时收到通知、知道停在哪、为什么。
- 各插件仓库里按 spec-guard 新流程开发的会话（Claude Code 或 Codex）：开完 PR 调一次 `hub run`，之后的合并、盯 CI 不归会话管。
- 只覆盖六个插件仓库和沙盒（总需求假设 A1、A2）。

## 使用场景

- **U1 普通 PR 自动合并**：新流程模块、合并档位为 `auto`、非 T4。会话开 PR 后调 `hub run`；hub 验证通过，写 `autopilot/verified`，打开 GitHub 自动合并（绑定验证过的提交）；GitHub 等必需检查通过后合并；`watch` 发现已合并，打标签、开跟进 issue、写汇报。用户这期间合盖休眠也不影响合并。
- **U2 T4 PR**：`hub run` 判为 T4，照样跑验证、写 `autopilot/verified`，但不打开自动合并，通知用户由用户在对话里说「合并」。
- **U3 PR 的 CI 变红**：`watch` 分类：环境问题自动重跑；CI 配置写错，通知用户；测试失败，通知负责的会话去修，同一原因最多修两次。
- **U4 主干 CI 变红**：分类后，测试失败就开降级 issue、立即收紧这个仓库的档位、通知用户；不撤回、不发版。
- **U5 验证后又推了新提交**：新提交没有 `autopilot/verified`，GitHub 不会合；`watch` 发现 head 变了，关掉自动合并，通知会话重新调 `hub run`。
- **U6 等太久**：自动合并打开 60 分钟还没合、单次 CI 超过 60 分钟，进入暂停并通知用户。
- **U7 回滚**：用户说暂停自动驾驶时，冻结 → 关掉所有排队中的自动合并 → 必要时退回直接合并（`mergeMode: direct`）。

## 业务规则和异常情形

- **R4 风险分级**：只有这几类判 T4：`.github/workflows/`、发布配置和版本号文件、权限令牌密钥配置、hub 自己的接管配置。`spec/`、`tasks/` 等流程文件不再判 T4。T4 永远不打开自动合并，这是调用打开接口之前的硬性前置条件，判定写进证据评论。
- **只合验证过的提交**：打开自动合并时带 `expectedHeadOid=validatedHeadOid`；`autopilot/verified` 只写在验证过的那个提交上。这个状态只表示「合并前验证通过」，不表示「可以自动合并」。
- **检查已全绿时**：GitHub 拒绝打开自动合并（沙盒实测：报 `unstable status`），这时按验证过的提交直接合并（现有的带 sha 合并）。推送后马上调用会报 head 对不上，要短暂重试，不能当成 head 被改了。
- **CI 三分类**（R6）：环境问题（失败在测试之前的 step，或重跑后变绿）自动重跑最多两次，不收紧；CI 配置写错，通知用户，修改是 T4；其余一律按测试失败，判不准往严里判。
- **修复上限**：同一项检查、同一条回归用例、同一条审查意见算同一原因，共用两次上限。修复时改了已有的测试文件或回归测试文档（以需求开工基线为准，新增文件不算），立即暂停交用户。
- **暂停**：持久的终态；只有用户明说、或重新验证通过才离开。PR 暂停时关闭自动合并。
- **不丢、不重做**：每个副作用（打标签、开 issue、发评论、发通知）带幂等键，做完逐项记下；通知先入队，发成功才出队。
- **单实例**：`watch` 同一时间只跑一个。
- **自动连着做之前先说一句**：`hub run`、`watch` 的每一串动作，先写一条「将要做什么」进汇报，并通知负责的会话。
- **回滚开关**：`~/.autopilot/config.json` 的 `mergeMode`（`automerge`｜`direct`，默认 `automerge`）；`watch --freeze` 之后只做关闭类动作。

## 不做什么

- 不做发版（模块 3 `hub-release`）；主干绿后只记下，不触发发版。
- 不改 spec-guard 的关卡和档位规则（模块 4、5）。
- 不做汇报的汇总成文（模块 8）；本模块只把事件写进 `watch-state.json` 和证据评论。
- 不自动撤回已合并的改动，不替用户关降级 issue。
- 不给六个仓库加必需检查 `autopilot/verified`、不装 launchd、不升钉（B 批，由 ecosystem-lead 组织，用户在 GitHub 上做）。
- 不迁移老流程模块。

## 成功标准

- **S1** 沙盒里一个非 T4 的新流程 PR，调一次 `hub run` 后由 GitHub 自动合并，合并提交就是写了 `autopilot/verified` 的那个提交；这期间没有任何本机进程在等。（总需求 S3）
- **S2** T4 的 PR 拿到 `autopilot/verified`，但没有被打开自动合并，用户收到「由你合并」的通知。（S4）
- **S3** 合并前验证没通过的 PR 既没有 `autopilot/verified`，也没有被打开自动合并。（S5）
- **S4** 打开自动合并后再推一个提交：GitHub 不合并新提交；下一轮 `watch` 关掉自动合并并通知会话。
- **S5** 检查已全绿时调 `hub run`：退回直接合并，合并的是验证过的提交。
- **S6** PR 上的 CI 失败按三种分：环境问题重跑、绿了继续、不收紧；配置问题通知用户；测试失败通知会话，同一原因修第三次前停下交用户。（S18）
- **S7** 主干 CI 因测试失败变红：开降级 issue、该仓库档位立即收紧、用户收到通知；没有撤回，也没有触发任何发版。（S19）
- **S8** 自动合并打开 60 分钟未合、或单次 CI 超过 60 分钟：进入暂停并通知用户，不空等。（S11）
- **S9** 修复时改了已有测试或回归测试文档：立即暂停，交用户。
- **S10** 回滚第 1～3 步在沙盒逐步验证通过：冻结后 `watch` 没有新的打开事件；排队中的自动合并全部关掉；`mergeMode=direct` 时 `hub run --dry-run` 显示走直接合并。
- **S11** `watch` 停了一段时间（模拟休眠）后再跑：从 `watch-state.json` 接着处理，不重复开 issue、不重复发通知。

## 待定问题

开工说明列的六件事，第 5 件已实测，其余给出建议，请确认：

- **Q1 风险分级怎么按 R4 改**（B0③）：建议改 hub 内置模板，T4 只留 R4 那四类；`spec/**`、`tasks/**` 降为普通文件（现在是 T4，`risk/tiers.py:116-120`）；没匹配上的文件默认从 T3 改为 T2，使能自动合并（现在只有 T0～T2 能自动合并，`risk/tiers.py:222`）。各仓库的 `.github/autopr/risk-tiers.json` 只放本仓库的补充类别，本身是 T4；hub 自己的这份在本模块里建。
- **Q2 检查已全绿时怎么合**（B0①）：按上面「检查已全绿时」那条：打开自动合并被拒绝（`unstable status` 或 `clean status`）就退回带 sha 的直接合并；其余错误照常停下。
- **Q3 老流程模块和 Dependabot 怎么拿到 `autopilot/verified`**（B0②）：建议 `hub run` 对老流程模块和不属于任何模块的 PR（含 Dependabot）只跑仓库检查和风险分级，通过就写 `autopilot/verified`、不打开自动合并，走人工路由用户说「合并」。Dependabot 的 PR 由用户或会话手动调一次 `hub run --pr N`。不另开管理员绕过（D1 已打开「管理员也受限」）。
- **Q4 App 权限**：hub 用 App 令牌实际写的是 contents、pull_requests、issues，外加本模块新增的 statuses（写提交状态）。check run 是各仓库 workflow 用自己的 GITHUB_TOKEN 写的，不用 App，所以 **Checks 建议降为只读**。CI 环境问题要重跑失败的 job，需要 **Actions 读写**：建议加到 App 上，重跑记在机器人名下，本机会话不在也能做。这两项要用户在 App 设置页改。
- **Q5 合并后主干 CI 会不会跑**：已实测（沙盒 #23，2026-11-27）：App 打开的自动合并合并后，主干 `push` CI 由 `haigeerlab-autopilot[bot]` 触发并通过，不用改成用户本人的身份。
- **Q6 Codex 会话推送、开 PR 时要审批**：建议本模块不做受控入口。长期授权第 1 条已经允许推本模块分支，开 PR 沿用 Plan 自动批准的授权，审批弹窗是 Codex 本机规则的事，归 A10（本机权限清单）。做受控入口等于让 hub 替会话推代码，扩大了 hub 的职责。
- **Q7 本需求的发版**：本模块合并后 hub 要不要发版、是否提前授权，等模块 3、4 上线后再按 R5 问；这次不问。
