## 目标

主干 CI 通过以后，不再等会话或用户来手动发版：hub 自己判断这一次能不能发、要不要停下，然后按发布流水线走完到本机安装和安装后验证。这一次发布内容涉及的需求都在确认时答了「做完自动发版：是」、而且授权没有作废的，直接发，不停下；其余的列出步骤清单停下，等用户确认一次后自动走完。版本 tag 由 hub 用 App 身份推（用户 2026-11-27 选 A，「选 A」）。这是自动驾驶第一版能力图第 3 行，对应总需求 R5、R6，成功标准 S6、S17；依据总体技术方案（已批）第 4.2、4.5、4.6、4.8、6、8 节，以及总账 `打tag授权办法-草稿.md`（用户选 A）。

## 给谁用

- 用户：只在需求确认时回答一次「做完自动发版吗？」；没有提前授权、授权作废，或清单里标了「要你动手」的步骤，才被找。用户本人是唯一审批人（总需求 A2）。
- 开发会话：不再自己推自动发版的版本 tag，也不用守着发版。
- 发版对象：总需求 A1 的试点仓库里有版本号的五个插件仓库（agent-relay、delegate-plugin、kb-plugin、spec-guard-plugin、module-crew）。autopilot-hub 也是试点仓库，但 hub 不发版本号（各仓库按 40 位提交引用 hub），不走发版。沙盒 autopilot-sandbox 只用于演练和验收，不算试点；验收前要按清单为它准备发布入口。
- 这些仓库都属个人账号，仓库所有者就是用户本人。仓库属于组织时，hub 认不出唯一审批人，发版一律停下交用户，组织仓库第一版不支持。

## 使用场景

1. **提前授权了**：一个需求的模块都合进主干，主干 CI 绿。watch 固定发版目标提交；hub 先只读地定出版本号，再核对这一次发布内容涉及的每个模块都授权有效、没有作废，然后按 `auto-confirm` 档自动走：打 tag（App 身份推）、等 Release 建好、装到本机、跑安装后验证。动手前把步骤清单写进汇报，不停下；走到 `restart-codex` 这类「要你动手」的步骤时通知用户，用户做完说一声再继续。
2. **没有提前授权或已作废**：hub 开发版跟踪 issue，列出这一次的每一步、标出哪几步要用户动手，停下。用户在 issue 里回复确认原话一次，hub 按清单自动走完清单里没标「要你动手」的步骤。
3. **作废**：发布内容里改到了 T4 路径，或者这次要升主版本号，提前授权按「没有」处理，走场景 2，汇报里写明作废原因。
4. **需求还没做完**：发布内容涉及的需求在能力图上还有模块没完成，这一次不自动发，等下一轮。
5. **主干又前进了**：发版期间别的 PR 合进主干，这一次仍只发已固定的目标提交；新提交等自己的主干 CI 跑完下一轮再处理。目标提交已经被更新的发版覆盖时，标「已覆盖」，不再发。
6. **主干出事了**：仓库已收紧、主干 CI 暂停、watch 全局冻结或有未关闭的降级 issue 时，不开始新发版，进行中的发版停在下一步之前。
7. **发出去以后才发现有问题**：安装后验证失败、发版之后主干 CI 变红，或会话用 `report-failure`（阶段 `release`，写明仓库和版本）报告了指向已发版本的故障，hub 通知用户并写明涉及的已发版本，不自动撤回、不删 tag、不删 Release。
8. **人批发版**：发布内容涉及的模块里有发版档位为人批的，或仓库没登记自动发版所需的入口，整次按人批发版处理：版本 tag 由 module-crew 凭用户原话推，或由 spec-guard 的会话在用户授权后用 `release.py` 推；hub 只做 tag 之后的发布。

## 业务规则和异常情形

### 能不能自动发、按什么档发

- **发布内容**：一次发版的内容是「上次发版的提交 → 发版目标提交」这段改动。上次发版的提交取仓库 `lastReleasedSha`；还没有记录时取发版目标提交之前（不含本次要发的 tag）最近一个版本 tag 指向的提交；人批交接时，本次的 tag 由交接方（module-crew 或 spec-guard 的会话）给出，它之前最近的版本 tag 才是上次；仓库一个版本 tag 都没有（首次发版）时，一律按人批发版处理。这段改动里合进来的每个 PR 对应到 spec-guard 的模块；对应不到模块的改动（未归属模块的 PR）按「没有提前授权」处理。
- **需求要做完**：发布内容涉及的每个模块所属的需求，在能力图上的模块都已完成（`/map --json` 状态为完成），而且这些模块的合并都已包含在发版目标提交里（目标提交是它们合并提交的后继），才进入下面的判定；否则这一次不发，等含全部合并的那次主干 CI 绿了再发。
- **每个模块各自判**：经 spec-guard `/map --json` 读每个模块的生效发版档位（`takeover.release`，已含模块覆盖、项目预设和收窄记录）和提前授权（`takeover.releasePreauth`，只在需求文档的 `release-preauth yes` 行在已批准、指纹有效的范围内时为 `true`）。hub 只经 `/map --json` 读，不自己解析需求文档；读不到字段按「没有」处理（总体方案第 8 节）。
- **合起来判，按这个先后**：
  1. 任一模块发版档位为人批 → 整次按人批发版处理（场景 8），不再看授权和作废；
  2. 否则，任一模块的生效发版档位低于 `auto-confirm`（包括被收窄到 `prepare`）、提前授权不为 `true`、或命中作废条件 → 按 `prepare` 跑，停下等用户确认（场景 2）；提前授权不会把收窄后的档位抬高；
  3. 否则这一次提前授权有效，按 `auto-confirm` 跑（场景 1）。
- **作废条件**只有两种，按每个模块的「需求开工基线 → 发版目标提交」这段改动判：①改到了 T4 路径（用 hub 现有风险分级判）；②要升主版本号。其他情况（例如中途修了两次）不影响授权，只写进汇报。取不到需求开工基线的，按作废处理。
- **先定版本号，再判授权**：发布引擎先跑 impact／定版本号这一步（只读，不推任何东西，由 impact 结论算出版本号，不再要求启动时预先给出版本号），拿到版本号和是否升主版本，再判授权、选档位。impact 没给出可识别的结论、或算不出版本号时，停下交用户。
- **上限**：hub 的上限现在对流水线自用插件（`pipeline_own`）一律压到 `prepare`，仓库上限只能往严里压（`pipeline/limits.py`）。本模块改上限逻辑：本次提前授权有效、或本次已有符合要求的确认时，五个插件的上限可到 `auto-confirm`；上限文件缺失、读不懂、或对该仓库明确压到更低时，仍按现有规则取低，这一次停下交用户。改上限文件和 `limits.py` 属 T4，要等本模块的授权核对上线后才放宽。

### 发版目标、顺序与前提

- watch 把主干 CI 绿的那次运行的 `head_sha` 固定为发版目标，只有这个提交的必需检查全部成功才触发。目标提交显式传进发布引擎；新发版、续跑、读流水线定义都用这个提交，不用当时的主干头。
- 每个仓库记 `lastReleasedSha`，按提交先后串行发，不倒序：目标是上次发版提交的后继才发，是祖先就标「已覆盖」。同一仓库同一时间只跑一次发版。
- 仓库已收紧、主干 CI 处于暂停、watch 全局冻结、或有未关闭的降级 issue 时，不开始新发版；进行中的发版在下一步之前停下，记暂停。

### 确认

- **停下等确认时**，hub 在发版跟踪 issue 里列出：仓库、发版目标提交、版本号、每一步（含要用户动手的几步）、无授权或作废的原因，以及整份清单的指纹（前 8 位）。
- **只认这样的确认**：仓库所有者本人（按 GitHub 用户 ID 认）在这份清单之后发的、没有编辑过的评论里，有独占一行的 `确认发版 <清单指纹前 8 位>`；引用块里的这一行、指纹对不上的、其他说法都不算。清单之后目标提交、版本号、步骤变了，清单重列、指纹变化，旧确认作废。
- **一次确认放行整份清单**：确认后，这一次发版按 `auto-confirm` 档继续，清单里没标「要你动手」的步骤都自动走，不再逐步停；标了「要你动手」的步骤到了那一步照样找用户。续跑用发版跟踪 issue 里记下的目标提交、版本号和清单，不重新解析。
- 命令行的 `--confirm` 入口只用于「要你动手」的步骤做完后告诉 hub 继续，不能当推 tag 的授权；推 tag 前一律按上面的规则核对 issue 里的原评论。

### 打 tag

- 推版本 tag 前必须核对到两样之一，都没有就停下、不推：①本次按上面的规则提前授权有效；②本次发版跟踪 issue 里有符合上面要求的确认。
- **入口契约**：仓库在 `.github/autopr/interface.yml` 登记 `release_publish`，hub 执行时通过环境变量传入 `AUTOPILOT_RELEASE_VERSION`（版本号，不带 `v`）和 `AUTOPILOT_RELEASE_TARGET`（发版目标提交 40 位）；命令只在本地创建附注 tag `v<版本号>` 指向这个提交，不推送、不建 Release。
- hub 在一次性克隆里、固定在发版目标提交上执行它，**执行时不给任何推送凭据**（保持现有发布步骤不给推送凭据的做法）。
- 执行完，hub 核对：本地只多了一个 tag，名字是 `v<版本号>`，解引用后指向发版目标提交。核对通过才用 hub App 的短期令牌只推这一个 tag 引用；不推分支、不推别的 tag。核对不过就停下。
- 推送前、以及中断后恢复时，先查远端：远端已有同名 tag 且解引用后指向发版目标提交，视为已推、不重推；远端同名 tag 指向别的提交，停下交用户。
- 仓库没登记 `release_publish` 的，按人批发版处理（场景 8），不替它打 tag。

### 建 Release 与之后的步骤

- tag 推上去以后，由仓库自己的 `release-tag.yml`（`on: push: tags: v*`）建 Release；人批发版也一样，Release 只有这一个创建方（spec-guard 补上 workflow 之前的过渡办法见下）。
- hub 等这个 tag 触发的那次 `release-tag.yml` 运行**整体成功结束**，再核对 Release 存在、对应这一个 tag、名字含这次的版本号、tag 指向发版目标提交；两样都满足才算 Release 就绪，继续装到本机、跑安装后验证。运行没触发、失败（即使 Release 已经建出来）、或超过单步时限，发版暂停并通知。
- spec-guard 现在没有 `release-tag.yml`，自动发版前要先补上（列在交给别家的清单里）。补上之前 spec-guard 只能人批发版，Release 照现状由会话在本机用 `release.py publish` 建，hub 核对 Release 存在、对应这个 tag 后再做之后的步骤；补上之后，人批也改由 `release-tag.yml` 建，`release.py` 不再建，始终只有一个创建方。

### 失败、超时、中断

- 任一步失败：发版进入暂停，通知用户和负责的会话，不自动换路线重试。
- 时限：发布单步超过 30 分钟（已批总体方案 4.6、第 7 节，沿用现有值），或等用户确认／「要你动手」的步骤超过 24 小时（Q1 已定），进入暂停并通知。
- 暂停是持久状态，记在 `watch-state.json`；只在用户明说或重新验证通过后离开（总体方案 4.6）。
- 每个副作用（推 tag、发评论、发通知、关 issue）都带幂等键、先记意图后做；中途断了，下一轮按意图对账远端（例如 tag 是否已在远端、指向哪个提交），不重做、不漏做。通知先进待发队列，成功才出队。
- 发版做完先记 `lastReleasedSha` 和完成记录，再关发版跟踪 issue。

### 其他

- **不撤回**：已经推出去的 tag、建好的 Release、装好的本机版本，hub 不自动撤回或删除；出了问题只通知用户，通知里写明涉及的版本、tag、Release 和证据链接。
- **先说一句**：自动发版开始前，先写一条「将要做什么」事件进汇报，并通知负责的会话（总体方案 4.8）。
- **人批发版不变**：版本 tag 仍由 module-crew（凭用户原话）或 spec-guard 的会话（用户授权后用 `release.py`）推；hub 只做 tag 之后的发布。

## 不做什么

- hub 不新增建 Release 的地方：Release 只由各仓库自己的 `release-tag.yml` 建（spec-guard 补一个和另外四家一致的）；hub 不建 Release，也不为此新增别的 Actions workflow。
- 不替别的插件改代码：交给别家的清单由 ecosystem-lead 转发，各家或用户做。
- 不撤回已发出的版本，不删 tag、Release。
- 不发 hub 自己。
- 第一版只做插件发版模板，不做 npm、网站发布模板（冻结中）；不支持组织仓库。
- 不改 module-crew 推 tag 的规矩（它只管人批发版）。

## 成功标准

- S1：需求确认时问了「做完自动发版吗？」并答了「是」、授权没作废的，需求的模块都完成、主干 CI 绿后，hub 自动走完到本机安装验证，中途除清单里「要你动手」的步骤外不找用户；步骤清单写进了汇报（总需求 S17）。
- S2：没有提前授权时，hub 列出完整步骤清单并标出要用户动手的步骤，停下；用户确认一次后，这一次按 `auto-confirm` 继续，清单里没标「要你动手」的步骤都自动走完（总需求 S6）。
- S3：改到 T4 路径时授权作废，按 S2 停下，汇报写明原因。
- S4：要升主版本号时授权作废，按 S2 停下；判定发生在只读定版本号之后、推 tag 之前；impact 没结论或算不出版本号时停下。
- S5：中途修了两次等其他情况不使授权作废，只写进汇报。
- S6：判定按先后：任一模块发版档位为人批，整次按人批处理（优先）；否则任一模块生效档位低于 `auto-confirm`（含收窄）、没授权、作废或取不到开工基线，整次按 S2 停下；需求还有模块没完成、或它们的合并不全在目标提交里时不发。
- S7：推 tag 前两样授权都没有时，hub 停下、不推 tag；命令行 `--confirm` 不能代替。
- S8：只认仓库所有者本人在最新清单之后、未编辑的、独占一行的 `确认发版 <指纹>`；引用、指纹不符、清单变了之后的旧确认都不算；组织仓库停下不支持。
- S9：`release_publish` 按入口契约拿到版本号和目标提交，执行时拿不到推送凭据；hub 只推解引用后指向发版目标提交的那一个 `v<版本号>` tag，tag 不符就停下；远端已有同名 tag 指向别的提交时停下。
- S10：tag 由 hub App 身份推上去后，由仓库的 `release-tag.yml` 建出 Release；hub 等这次运行整体成功、并核对 Release 对应这个 tag、版本和目标提交后再继续；运行没触发或失败（即使 Release 已建出）时暂停并通知。
- S11：只发固定的发版目标提交（新发版和续跑都是）；不倒序；已被覆盖的目标不再发；同一仓库同一时间只有一次发版；首次发版按人批处理；人批交接时不把本次的 tag 当成上次发版。
- S12：仓库收紧、主干 CI 暂停、全局冻结或有降级 issue 时，不开始新发版，进行中的停在下一步前。
- S13：任一步失败、单步超过 30 分钟、或等用户超过 24 小时，发版暂停并通知用户和会话；中途断了，下一轮不重做、不漏做。
- S14：安装后验证失败、发版后主干 CI 变红、或会话用 `report-failure --stage release` 报告已发版本有故障，hub 通知用户并写明涉及的已发版本；不自动撤回、不删 tag 和 Release。
- S15：上限文件缺失、读不懂或对仓库明确压档时，按现有规则取低并停下交用户；放宽只在本次授权有效或已确认时生效。
- S16：仓库没登记 `release_publish` 时按人批处理，不替它打 tag；人批发版仍由 module-crew 或 spec-guard 的会话推 tag，hub 只做之后的发布，行为不变。
