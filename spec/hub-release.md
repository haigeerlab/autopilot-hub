## 目标

主干 CI 通过以后，不再等会话或用户来手动发版：hub 自己判断这一次能不能发、要不要停下，然后按发布流水线走完到本机安装和安装后验证。这一次发布内容涉及的需求都在确认时答了「做完自动发版：是」、而且授权没有作废的，直接发，不停下；其余的列出步骤清单停下，等用户确认一次后自动走完。版本 tag 由 hub 用 App 身份推（用户 2026-11-27 选 A，「选 A」）。这是自动驾驶第一版能力图第 3 行，对应总需求 R5、R6，成功标准 S6、S17；依据总体技术方案（已批）第 4.2、4.5、4.6、4.8、6、8 节，以及总账 `打tag授权办法-草稿.md`（用户选 A）。

## 给谁用

- 用户：只在需求确认时回答一次「做完自动发版吗？」；没有提前授权、授权作废，或清单里标了「要你动手」的步骤，才被找。用户本人是唯一审批人（总需求 A2）。
- 开发会话：不再自己推版本 tag，也不用守着发版。
- 发版对象：总需求 A1 的试点仓库里有版本号的五个插件仓库（agent-relay、delegate-plugin、kb-plugin、spec-guard-plugin、module-crew）。autopilot-hub 也是试点仓库，但 hub 不发版本号（各仓库按 40 位提交引用 hub），不走发版。沙盒 autopilot-sandbox 只用于演练和验收，不算试点。

## 使用场景

1. **提前授权了**：一个需求的模块都合进主干，主干 CI 绿。watch 固定发版目标提交，hub 核对这一次发布内容涉及的每个模块都授权有效、没有作废，按 `auto-confirm` 档自动走：定版本号、打 tag（App 身份推）、等 Release 建好、装到本机、跑安装后验证。动手前把步骤清单写进汇报，不停下；走到 `restart-codex` 这类「要你动手」的步骤时通知用户，用户做完说一声再继续。
2. **没有提前授权或已作废**：hub 开发版跟踪 issue，列出这一次的每一步、标出哪几步要用户动手，停下。用户在 issue 里回复确认原话一次，hub 按清单自动走完清单里没标「要你动手」的步骤。
3. **作废**：发布内容里改到了 T4 路径，或者这次要升主版本号，提前授权按「没有」处理，走场景 2，汇报里写明作废原因。
4. **主干又前进了**：发版期间别的 PR 合进主干，这一次仍只发已固定的目标提交；新提交等自己的主干 CI 跑完下一轮再处理。目标提交已经被更新的发版覆盖时，标「已覆盖」，不再发。
5. **主干出事了**：仓库已收紧、主干 CI 暂停、或 watch 全局冻结时，不开始新发版，进行中的发版停在下一步之前。
6. **发出去以后才发现有问题**：通知用户，不自动撤回、不删 tag、不删 Release。
7. **人批发版**：发布内容涉及的模块里有发版档位为人批的，或仓库没登记自动发版所需的入口，照旧由 module-crew 或会话按原规矩推 tag，hub 只做 tag 之后的发布。

## 业务规则和异常情形

### 能不能自动发、按什么档发

- **发布内容**：一次发版的内容是「上次发版的提交 `lastReleasedSha` → 发版目标提交」这段改动；其中合进来的每个 PR 对应到 spec-guard 的模块。对应不到模块的改动（未归属模块的 PR）按「没有提前授权」处理。
- **每个模块各自判**：经 spec-guard `/map --json` 读每个模块的生效发版档位（`takeover.release`，已含模块覆盖、项目预设和收窄记录）和提前授权（`takeover.releasePreauth`，只在需求文档的 `release-preauth yes` 行在已批准、指纹有效的范围内时为 `true`）。hub 只经 `/map --json` 读，不自己解析需求文档；读不到字段按「没有」处理（总体方案第 8 节）。
- **合起来判**：发布内容涉及的所有模块都满足「发版档位允许自动、提前授权为 `true`、没作废」，这一次才算提前授权有效，按 `auto-confirm` 跑；任一模块不满足，按 `prepare` 跑、停下等用户确认；任一模块发版档位为人批，整次按人批发版处理（场景 7）。
- **作废条件**只有两种，按每个模块的「需求开工基线 → 发版目标提交」这段改动判：①改到了 T4 路径（用 hub 现有风险分级判）；②要升主版本号。其他情况（例如中途修了两次）不影响授权，只写进汇报。
- **先定版本号，再判授权**：发布引擎先跑 impact／定版本号这一步（只读，不推任何东西），拿到版本号和是否升主版本，再判授权、选档位；升主版本就作废，按 `prepare` 停下。
- **上限放宽**：hub 的上限现在对流水线自用插件（`pipeline_own`）一律压到 `prepare`，仓库上限只能往严里压（`pipeline/limits.py`）。本模块改上限逻辑：提前授权有效的这一次，五个插件的上限都可到 `auto-confirm`；其余情况维持现状。改上限文件和 `limits.py` 属 T4，要等本模块的授权核对上线后才放宽。

### 发版目标、顺序与前提

- watch 把主干 CI 绿的那次运行的 `head_sha` 固定为发版目标，只有这个提交的必需检查全部成功才触发。目标提交显式传进发布引擎；新发版、续跑、读流水线定义都用这个提交，不用当时的主干头。
- 每个仓库记 `lastReleasedSha`，按提交先后串行发，不倒序：目标是 `lastReleasedSha` 的后继才发，是祖先就标「已覆盖」。同一仓库同一时间只跑一次发版。
- 仓库已收紧（`repos.narrowed`）、主干 CI 处于暂停、watch 全局冻结、或有未关闭的降级 issue 时，不开始新发版；进行中的发版在下一步之前停下，记暂停。

### 确认

- **停下等确认时**，hub 在发版跟踪 issue 里列出：仓库、发版目标提交、版本号、每一步（含要用户动手的几步）、作废或无授权的原因，并给清单一个摘要（指纹）。
- **只认这样的确认**：仓库所有者本人（按 GitHub 用户 ID 认，不按名字）在这份清单之后发的、没有编辑过的评论，原话里写明确认（例如「确认发版」），且清单之后目标提交、版本号、步骤都没变。清单变了要重新列、重新确认。
- **一次确认放行整份清单**：确认后，清单里没标「要你动手」的步骤都自动走，不再逐步停；标了「要你动手」的步骤到了那一步照样找用户。续跑用发版跟踪 issue 里记下的目标提交和清单，不重新解析。

### 打 tag

- 推版本 tag 前必须核对到两样之一，都没有就停下、不推：①本次按上面的规则提前授权有效；②本次发版跟踪 issue 里有符合上面要求的确认原话。
- 仓库在 `.github/autopr/interface.yml` 登记 `release_publish`：只在本地创建附注 tag，不推送、不建 Release。hub 在一次性克隆里、固定在发版目标提交上执行它，**执行时不给任何推送凭据**（保持现有发布步骤不给推送凭据的做法）。
- 执行完，hub 核对：本地只多了一个 tag，名字是 `v<版本号>`，指向发版目标提交。核对通过才用 hub App 的短期令牌只推这一个 tag 引用；不推分支、不推别的 tag。核对不过就停下。
- 仓库没登记 `release_publish` 的，按人批发版处理（场景 7），不替它打 tag。

### 建 Release 与之后的步骤

- tag 推上去以后，由仓库自己的 `release-tag.yml`（`on: push: tags: v*`）建 Release。hub 等 Release 出现，再继续装到本机、跑安装后验证。
- spec-guard 现在没有 `release-tag.yml`，自动发版前要先补上（列在交给别家的清单里）；补上之前 spec-guard 只能人批发版。

### 失败、超时、中断

- 任一步失败：发版进入暂停，通知用户和负责的会话，不自动换路线重试。
- 时限：单步执行超过 60 分钟、或等用户确认／「要你动手」的步骤超过 24 小时，进入暂停并通知（时限待用户确认，见待定问题）。
- 暂停是持久状态，记在 `watch-state.json`；只在用户明说或重新验证通过后离开（总体方案 4.6）。
- 每个副作用（推 tag、发评论、发通知、关 issue）都带幂等键、先记意图后做；中途断了，下一轮按意图对账远端（例如 tag 是否已在远端），不重做、不漏做。通知先进待发队列，成功才出队。
- 发版做完先记 `lastReleasedSha` 和完成记录，再关发版跟踪 issue。

### 其他

- **不撤回**：已经推出去的 tag、建好的 Release、装好的本机版本，hub 不自动撤回或删除；出了问题只通知用户。
- **先说一句**：自动发版开始前，先写一条「将要做什么」事件进汇报，并通知负责的会话（总体方案 4.8）。
- **人批发版不变**：版本 tag 仍由 module-crew（凭用户原话）或会话按原规矩推；hub 只做 tag 之后的发布。

## 不做什么

- 不改各仓库现有的 `release-tag.yml`，不把建 Release 搬进 hub 或 Actions。
- 不替别的插件改代码：交给别家的清单由 ecosystem-lead 转发，各家或用户做。
- 不撤回已发出的版本，不删 tag、Release。
- 不发 hub 自己。
- 第一版只做插件发版模板，不做 npm、网站发布模板（冻结中）。
- 不改 module-crew 推 tag 的规矩（它只管人批发版）。

## 成功标准

- S1：需求确认时问了「做完自动发版吗？」并答了「是」、授权没作废的，主干 CI 绿后 hub 自动走完到本机安装验证，中途除清单里「要你动手」的步骤外不找用户；步骤清单写进了汇报（总需求 S17）。
- S2：没有提前授权时，hub 列出完整步骤清单并标出要用户动手的步骤，停下；用户确认一次后，清单里没标「要你动手」的步骤都自动走完（总需求 S6）。
- S3：改到 T4 路径时授权作废，按 S2 停下，汇报写明原因。
- S4：要升主版本号时授权作废，按 S2 停下；判定发生在定版本号之后、推 tag 之前。
- S5：中途修了两次等其他情况不使授权作废，只写进汇报。
- S6：发布内容涉及多个模块时，任一模块没授权或作废，整次按 S2 停下；任一模块发版档位为人批，整次按人批处理。
- S7：推 tag 前两样授权都没有时，hub 停下、不推 tag。
- S8：只认仓库所有者本人在最新清单之后、未编辑的确认原话；清单变了旧确认不算。
- S9：`release_publish` 执行时拿不到推送凭据；hub 只推指向发版目标提交的那一个 `v<版本号>` tag，tag 不符就停下。
- S10：tag 由 hub App 身份推上去后，由仓库的 `release-tag.yml` 建出 Release，hub 等到 Release 再继续。
- S11：只发固定的发版目标提交（新发版和续跑都是）；不倒序；已被覆盖的目标不再发；同一仓库同一时间只有一次发版。
- S12：仓库收紧、主干 CI 暂停、全局冻结或有降级 issue 时，不开始新发版，进行中的停在下一步前。
- S13：任一步失败或超过时限，发版暂停并通知用户和会话；中途断了，下一轮不重做、不漏做；已发出的版本不自动撤回。
- S14：仓库没登记 `release_publish` 时按人批处理，不替它打 tag；人批发版仍由 module-crew 推 tag，hub 只做之后的发布，行为不变。
