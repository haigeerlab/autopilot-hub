## 目标

主干 CI 通过以后，不再等会话或用户来手动发版：hub 自己判断这一次能不能发、要不要停下，然后按发布流水线走完到本机安装和安装后验证。需求确认时用户答了「做完自动发版：是」、而且授权没有作废的，直接发，不停下；其余的列出步骤清单停下等用户确认。版本 tag 由 hub 用 App 身份推（用户 2026-11-27 选 A，「选 A」）。这是自动驾驶第一版能力图第 3 行，对应总需求 R5、R6，成功标准 S6、S17；依据总体技术方案（已批）第 4.2、4.5、4.6、4.8、6 节，以及总账 `打tag授权办法-草稿.md`（用户选 A）。

## 给谁用

- 用户：只在需求确认时回答一次「做完自动发版吗？」；没有提前授权、授权作废，或清单里标了「要你动手」的步骤，才被找。
- 开发会话：不再自己推版本 tag，也不用守着发版。
- 六个被发版的仓库：五个插件仓库（agent-relay、delegate、kb、module-crew、spec-guard）和沙盒 autopilot-sandbox。hub 自己不发版本号，不在其内。

## 使用场景

1. **提前授权了**：一个模块合进主干，主干 CI 绿。watch 固定发版目标提交，hub 读到这个模块的提前授权有效、没有作废，按 `auto-confirm` 档自动走：定版本号、打 tag（App 身份）、等各仓库 `release-tag.yml` 建 Release、装到本机、跑安装后验证。动手前把步骤清单写进汇报，不停下；走到 `restart-codex` 这类「要你动手」的步骤时通知用户，用户做完说一声再继续。
2. **没有提前授权或已作废**：hub 开发版跟踪 issue，列出这一次的每一步并标出哪几步要用户动手，停下。用户在 issue 里回复确认原话后，hub 按清单自动走完。
3. **作废**：从需求开工基线到发版目标提交之间改到了 T4 路径，或者这次要升主版本号，提前授权按「没有」处理，走场景 2，汇报里写明作废原因。
4. **主干又前进了**：发版期间别的 PR 合进主干，这一次仍只发已固定的目标提交；新提交等自己的主干 CI 跑完下一轮再处理。目标提交已经被更新的发版覆盖时，标「已覆盖」，不再发。
5. **发出去以后才发现有问题**：通知用户，不自动撤回、不删 tag、不删 Release。
6. **人批发版**：模块的发版档位是人批（不是自动）时，照旧由 module-crew 或会话按原规矩推 tag，hub 只做 tag 之后的发布。

## 业务规则和异常情形

- **推 tag 前的授权核对**：hub 推版本 tag 之前必须核对到下面两样之一，都没有就停下、不推：
  1. spec-guard `/map --json` 里这个模块的提前授权有效：`takeover.releasePreauth` 为 `true`（spec-guard 只在需求文档的 `release-preauth yes` 行在已批准、指纹有效的范围内时给 `true`），且没有命中作废条件；
  2. 本次发版跟踪 issue 里，仓库所有者在最新清单之后、没有编辑过的确认原话。
- hub 只经 spec-guard 的 `/map --json` 读提前授权，不自己解析需求文档；读不到这个字段按「没有提前授权」处理。
- **作废条件**只有两种，按「需求开工基线 → 发版目标提交」这段改动判：①改到了 T4 路径（用 hub 现有风险分级判）；②要升主版本号（发布引擎的 impact 步骤给出）。其他情况（例如中途修了两次）不影响授权，只写进汇报。
- **发版档位**：授权有效时这一次按 `auto-confirm` 跑；没有或作废时按 `prepare` 跑，停在 `approve` 等确认。hub 的上限文件把六个插件放宽到 `auto-confirm`（改上限文件属 T4，要等本模块的授权核对上线后再放宽）。
- **发版目标与顺序**：watch 把主干 CI 绿的那次运行的 `head_sha` 固定为发版目标，只有这个提交的必需检查全部成功才触发；每个仓库记 `lastReleasedSha`，按提交先后串行发，不倒序；同一仓库同一时间只跑一次发版。
- **打 tag**：hub 在一次性克隆里、固定在发版目标提交上，执行仓库在 `.github/autopr/interface.yml` 登记的 `release_publish` 命令，tag 用 hub App 的短期令牌推送；推上去以后照旧由各仓库的 `release-tag.yml` 建 Release。仓库没登记 `release_publish` 的，停下交用户，不替它打 tag。
- **步骤清单**：不管停不停，动手前都列出这一次要做的每一步和其中要用户动手的几步，写进汇报（提前授权时）或发版跟踪 issue（停下时）；清单以外不做额外的事。
- **失败与等太久**：任一步失败、或某一步等待超过时限，发版进入暂停，通知用户和负责的会话，不自动重试别的路线；暂停只在用户明说或重新验证通过后离开。
- **不撤回**：已经推出去的 tag、建好的 Release、装好的本机版本，hub 不自动撤回或删除；出了问题只通知用户。
- **先说一句**：自动发版开始前，先写一条「将要做什么」事件进汇报，并通知负责的会话（总体方案 4.8）。
- **人批发版不变**：发版档位为人批时，版本 tag 仍由 module-crew（凭用户原话）或会话按原规矩推；hub 只做 tag 之后的发布。

## 不做什么

- 不改各仓库现有的 `release-tag.yml`，不把建 Release 搬进 hub 或 Actions。
- 不替别的插件改代码：spec-guard 的 `release.py publish` 拆两段、各仓库登记 `release_publish`、六个仓库加 tag 规则集，列成清单交 ecosystem-lead 转发，由各家或用户做。
- 不撤回已发出的版本，不删 tag、Release。
- 不发 hub 自己（hub 不发版本号，各仓库按 40 位提交引用 hub）。
- 第一版只做插件发版模板，不做 npm、网站发布模板（冻结中）。
- 不改 module-crew 推 tag 的规矩（它只管人批发版）。

## 成功标准

- S1：提前授权有效且没作废时，主干 CI 绿后 hub 自动走完到本机安装验证，中途除清单里「要你动手」的步骤外不找用户；步骤清单写进了汇报（对应总需求 S17）。
- S2：没有提前授权、或作废（改到 T4、升主版本号）时，hub 列出完整步骤清单并标出要用户动手的步骤，停下；用户确认后自动走完（对应总需求 S6）。
- S3：推 tag 前两样授权都没有时，hub 停下、不推 tag。
- S4：版本 tag 由 hub App 身份推送，推上去后由仓库的 `release-tag.yml` 建出 Release。
- S5：只发固定的发版目标提交；不倒序；已被覆盖的目标不再发；同一仓库同一时间只有一次发版。
- S6：任一步失败或等太久，发版暂停并通知用户和会话；已发出的版本不自动撤回。
- S7：仓库没登记 `release_publish` 时停下交用户，不替它打 tag。
- S8：人批发版仍由 module-crew 推 tag，hub 只做之后的发布，行为不变。
