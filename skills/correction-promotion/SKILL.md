# 纠错晋升

要改的是仓库，不是提示词。目标是：一处改动只看所在的那个文件是对的，放到整个仓库里也必须是对的。（出处：pstack `/correct`）

规格见 `docs/spec/slice-6.md`。纠正事件记成被纠正仓库里的 issue，标签 `correction` 加 `correction:<类名>`；同一类第 2 次出现时，系统开「晋升候选」issue（标签 `correction:candidate`）并问"要不要沉淀成规则？"。只有用户说"沉淀"之后才走本 skill，从不自动做。

## 怎么记一条纠正、怎么对类名

在 autopilot-hub 的检出里运行（`<hub>` 指它的路径）：

```bash
# 先看这个仓库已有哪些类名和次数，尽量对上已有的类名
python3 -B <hub>/correction/cli.py classes --repo <owner/name> [--json]

# 记一条：类名是小写英文加连字符（如 weakened-assertion），对不上已有的就起新名，新名要先给用户看
python3 -B <hub>/correction/cli.py record --repo <owner/name> --class <类名> --summary "<一句话：错在哪、该怎样>" [--ref <PR、提交或会话链接>]
```

- 用户在会话里纠正 AI，或 AI 判断这是一次纠正时，记之前先把类名和一句话给用户看。
- 同一类名下同一个 `--ref` 不会重复记；退出码 0 成功、2 参数不对、1 GitHub 调用失败（失败时什么都没写）。
- 切片 2 的撤回降级会自动记一条 `revert` 类，不用手记。
- `record` 的输出里出现"要不要沉淀成规则？"，就把候选 issue 链接和这句话转给用户，等答复。

## 输入

- 错误类名 `correction:<类名>`，以及该类下的全部纠正事件 issue（候选 issue 里有列表）
- `CLAUDE.md` 里的"规则 ↔ 执行者"表；没有就新建

## 步骤

1. **确认这是一个类。** 用一句话写出错误写法，再用一句话写出正确写法。事件不足 2 条，或者找不出清楚的共同点，就回报 `not-a-class` 并停止。
2. **检查前提。** 如果同一前提下已经修过两次以上还没修好，先把这个前提写下来，验证它成立再继续。
3. **从最高层往下逐层判断。** 每一层都要写明能做或不能做的理由：
   - Q1 架构：能不能让错误写法根本没有入口（收进唯一模块、改目录边界、删掉旧 API、合并重复的数据源）？
   - Q2 类型或数据结构：能不能让错误状态无法表达？
   - Q3 检查器：能不能用 AST、正则或依赖图把它找出来？
   - Q4 测试：是不是只能在运行时观察到？如果是，测行为，不测实现。
   - Q5 规则：以上都做不到时，写成规则并附一个失败示例；在规则表里登记"执行者：无"，同时开一个 backlog issue。

   允许过渡做法：先用 Q3 止血，再开 issue 跟踪 Q1；等 Q1 落地，删掉这个检查器。
4. **检查器的报错按以下六行写。**

   ```text
   <规则名>: <这一行违反了什么>
   为什么：<具体后果>
   改成：<应该用的函数、文件或写法，附一行示例>
   不要：<最常见的绕过方式>
   例外：只能写在本行，格式 `# autopilot-allow <规则名>: <理由> until <YYYY-MM-DD> approved-by <人>`
   详见：<规则表条目链接>
   ```

   如果这种写法在仓库里已经很普遍，检查器只拦新增的行。仓库约定了一正一反测试的，照约定补测试；仓库有变异测试的，给新断言补上变异体。
   豁免只能写在出错的那一行，必须带过期日和审批人；旧写法 `autopr-allow` 仍被识别。hub 里已有三个现成检查（`rules/`：`no-weakened-assertion`、`suppression-budget`、`chinese-commit`），可照它们的结构写。
5. **证明检查器会失败。** 在至少一个真实的历史出错提交上跑新检查，贴出失败输出；再在当前 main 上跑一遍，贴出通过输出。本地和 CI 要跑同一条命令。没有失败证明，就不算完成。
6. **清理存量。** 存量少，就在同一个 PR 里分两个提交：先加检查，再迁移存量。存量多，另开 issue。
7. **更新规则表。** 按下面的格式加一行：

   | 规则 | 执行者 | 晋升 PR | 首次事件 |
   | --- | --- | --- | --- |
   | … | `scripts/check-xxx.py` | #N | #M |

   如果执行者已经让这个错误不可能再发生，就删掉 prose 里的对应规则。
8. **开 PR，然后交审。** 一个错误类对应一个 PR，标题写 `fix(guard): <类名>`，正文写清错误类、证据和选的层。风险档按仓库的 `risk-tiers.json` 计算：新增检查器通常是 T2，改到 `validate.sh` 或 CI 的是 T4。**晋升 PR 先交 Codex 审，审过之后由用户合并**；AI 不自己合并。晋升候选 issue 在 PR 合并后关闭。

## 回复

回复里要包含：错误类和全部证据、选了哪一层以及更高的层为什么不行、失败证明与通过证明、规则表的变化。

## 不要做

- 不要只加一条 prose 规则就结束，除非已经写明 Q1–Q4 都不可行。
- 不要放宽或删除已有检查。这类改动属于 T4，只能由人来做。
- 不要把产品功能修复混进同一个 PR。
- 没有失败证明时，不要说这个错误"已防止"。
- 不要在用户说"沉淀"之前就开晋升 PR。
